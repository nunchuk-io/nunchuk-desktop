# Reproducible builds

This directory contains the reference build environment used to verify that a
release artifact was produced from the published source.

## Current status

| Platform | Status | Reference artifact |
| --- | --- | --- |
| Linux x86_64 | Qt 6 reference build | `nunchuk-linux-v<VERSION>.zip` |
| macOS x86_64/arm64 | Reproducibility-gated, Developer ID signed and notarized | `nunchuk-macos-<ARCH>-v<VERSION>.dmg` |
| Windows x64 | Reproducibility-gated and Authenticode signed | `nunchuk-windows-x64-v<VERSION>-setup.exe` |

The Linux builder uses Qt 6.11.1 and OpenSSL 3.5.7 LTS. It pins the container base
digest, GCC/binutils paths, Qt module set, source dependency commits, linuxdeploy
and linuxdeploy-plugin-qt bytes, downloaded release artifacts, and the AppImage
runtime. `SOURCE_DATE_EPOCH` is derived from the source commit.

macOS and Windows use the same Qt/OpenSSL versions. Their two clean unsigned
replicas must compare byte-for-byte before the protected `release-signing`
environment can access Apple or Azure credentials. Service-issued signing
timestamps and Apple notarization tickets mean the final signed files are not
expected to be byte-identical across signing runs; published release manifests
bind each signed artifact to the digest of the reproducible unsigned payload.

## Linux prerequisites

- Git
- Docker with Buildx
- An x86_64 host, or a Docker installation capable of running `linux/amd64`
- Access to the recursive source submodules

## Build an exact Linux version

The release tag is expected to use the numeric form `2.6.7`, without a leading
`v`.

```bash
export PROJECT_DIR="$HOME/nunchuk-desktop"
export VERSION="2.6.7"

git clone https://github.com/nunchuk-io/nunchuk-desktop "$PROJECT_DIR"
cd "$PROJECT_DIR"
git checkout --detach "$VERSION"
git submodule update --init --recursive

export SOURCE_DATE_EPOCH="$(git show -s --format=%ct HEAD)"

docker buildx build \
  --platform linux/amd64 \
  --load \
  --file reproducible-builds/Dockerfile.linux \
  --tag nunchuk-builder-linux-amd64:qt6 \
  .

docker run --platform linux/amd64 --rm \
  --env TAG="$VERSION" \
  --env SOURCE_DATE_EPOCH="$SOURCE_DATE_EPOCH" \
  --volume "$PROJECT_DIR:/project" \
  --workdir /project \
  nunchuk-builder-linux-amd64:qt6 \
  bash reproducible-builds/build_linux.sh
```

The build produces:

```text
nunchuk-linux-v<VERSION>/nunchuk-linux-v<VERSION>.zip
nunchuk-linux-v<VERSION>/nunchuk-linux-v<VERSION>.zip.sha256
```

Verify the checksum generated by the build:

```bash
cd "$PROJECT_DIR/nunchuk-linux-v$VERSION"
sha256sum --check "nunchuk-linux-v$VERSION.zip.sha256"
```

## Compare the Linux release

Download the release ZIP and its `.sha256` file from GitHub. First validate the
downloaded checksum, then compare the official and locally produced files:

```bash
sha256sum --check "nunchuk-linux-v$VERSION.zip.sha256"
cmp \
  "nunchuk-linux-v$VERSION.zip" \
  "$PROJECT_DIR/nunchuk-linux-v$VERSION/nunchuk-linux-v$VERSION.zip"
```

No output from `cmp` means that the two ZIP files are byte-for-byte identical.
For a mismatch, retain both ZIP files and inspect them with `diffoscope`.

## Signed macOS and Windows releases

The macOS workflow builds native Intel and Apple Silicon payloads twice on
separate runners. It signs nested code from the inside out, signs the outer
DMG, submits that DMG to Apple, staples the accepted ticket and runs Gatekeeper
checks. See `reproducible-builds/README-macos.md` for the exact input lock,
entitlements and verification boundary.

The Windows workflow builds twice with native MSVC 2022 because Qt WebEngine is
not supported by the MinGW build used by the old Qt 5 container. It compares
the canonical unsigned ZIP and Inno Setup installer, signs the selected
application payload with Azure Artifact Signing, rebuilds the installer from
that signed payload, then Authenticode-signs and verifies the installer. The
published release manifest records the unsigned payload digest, signer and
signed artifact hashes. See `reproducible-builds/README-windows.md` for the
dependency lock and signing configuration.

Only tag builds publish GitHub release assets. All three publish jobs share one
queued concurrency group and never replace an existing asset with different
bytes. GitHub artifact attestations are created only after the immutable asset
gate accepts the release files.

## Reproducibility boundary

The GitHub workflow performs two clean out-of-source application builds in the
same pinned builder image, checks that the first build did not modify tracked
source files, and refuses to publish when their ZIP hashes differ. This catches
non-determinism in compilation, deployment, AppImage creation, and ZIP creation.

Packaging uses a two-pass Qt 6 deployment. The first pass resolves the
application and QML imports; the second pass closes the dependency graph for
every ELF added by the Qt plugin. Before publication, CI extracts the final
AppImage and checks its desktop entry, custom launcher, Qt plugin allowlist,
Qt5Compat/ShaderTools pairing, WebEngine resources, pinned OpenSSL runtime, HWI,
XCB platform backend, minizip, and unresolved ELF dependencies.

The build still obtains Ubuntu packages, Qt archives, and the two linuxdeploy
assets from upstream repositories while creating the builder image. Downloaded
deployment tools are rejected unless their SHA-256 hashes match the recorded
commits, but the upstream `continuous` asset URLs are not archival mirrors.
Long-term verification therefore depends on those exact inputs remaining
available. A fully hermetic archive would require mirroring every Debian/Qt
package and deployment-tool binary used by the image.

The macOS/Windows lock files pin dependency versions, commits and downloaded
archive hashes, and both workflows record their native toolchain fingerprint.
GitHub-hosted runner images, Qt/PyPI distribution services and Windows SDK
components are nevertheless external inputs rather than an archived hermetic
toolchain. The two-replica gates prove determinism for the selected CI inputs;
long-term independent rebuilding additionally requires mirroring those inputs
or using versioned self-hosted runner images.
